## Current checkpoint — grid-first Tileset Contract V2
The previous sheet-first approach is abandoned as the production path.

Canonical rule:

**Define the runtime grid and exact asset boxes first. Generate isolated transparent sprites second. Pack atlases only as a deterministic build output.**

Verified runtime facts:
- map grid is 13 x 13 cells,
- rooms may span multiple joined cells,
- logical V2 art cell is 32 x 32 px,
- full map at 1x is 416 x 416 CSS px,
- map should pan/clip/focus rather than fractionally stretch the tile grid.

## Binding size standard
`visual/ASSET_SIZE_STANDARD_V2.md` and `visual/asset-size-standard-v2.json` define all canonical production boxes currently allowed.

Important locked sizes:
- floor / wall / corner / connection canvas: **32 x 32 px**,
- structural wall depth: **6 px**,
- door/opening span: **20 px** centred in a 32 px cell,
- hero/NPC/monster map sprite: **32 x 32 canvas**, max **24 x 28** visible, baseline y=30,
- generic map marker: **32 x 32 canvas**, max **24 x 24** visible,
- small map/item marker: **32 x 32 canvas**, max **22 x 22** visible,
- generic UI icon: **24 x 24 canvas**, max **20 x 20** visible,
- optional repeatable UI ornament: **16 x 16 px**, never stretched,
- runtime atlas: **512 x 512**, 16 x 16 slots of 32 px,
- existing Asset Contract 2.4.0 character/item/scene/symbolic sizes remain preserved.

Do not invent a new asset size during production. If a genuinely new visual role needs a different box, update the size standard + machine-readable JSON + regression test first, then produce the asset.

## V2 source-vs-atlas rule
Source of truth is individual normalized PNG files.

The atlas is generated by script from a manifest. Never manually crop a finished generated sheet.

Generation sequence:
1. one isolated sprite/segment per generated source,
2. true transparent background where required,
3. normalize to exact logical box from the size standard,
4. validate dimensions/alpha/safe area,
5. deterministic atlas packing.

## First production scope
No room contents yet.

Build structural dungeon art only:
- 9 neutral 32x32 floor stone variants,
- 4 straight wall orientations,
- 4 outer/convex corners,
- 4 inner/concave corners.

Floor variants are semantic-neutral and rotation-safe. Nine variants x four rotations provide up to 36 visual combinations without adding story meaning.

Walls/corners are transparent 32x32 overlays aligned exactly to cell edges. Directional wall sprites are authored per orientation; do not rotate lit wall art blindly.

## Layer model
1. fog/background = CSS/runtime state
2. floor tile
3. wall/corner overlay
4. connection/door overlay
5. hero/marker/content sprite
6. current/selected/reachable/focus = CSS/runtime state

This supports 1x1, rectangular, L-shaped and irregular multi-cell rooms using the same asset bank.

## Hard rules
- no checkerboard/matte background baked into sprites,
- no manual crop coordinates in production,
- no stretched sheet bitmap as UI chrome,
- no environment/story meaning inferred from tone,
- no current/selected state baked into art,
- no characters/items/furniture in structural tiles,
- no content-bank expansion,
- no changes to runtime gameplay/state.

## Historical visual attempts
V1.3 and V1.4 are retained as lessons, not the current production method.

Important retained lessons:
- structural/browser QA does not prove visual quality,
- full generated sheets are too imprecise to crop reliably,
- stretched bitmap chrome fails,
- multi-cell rooms need room-level geometry,
- art may not invent topology/content/state,
- mobile surfaces must not overlay canonical controls.
